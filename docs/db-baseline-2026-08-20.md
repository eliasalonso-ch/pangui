## Disk IO Budget investigation — CLOSED, no action

Cause: `wal_buffers = 492 * 8kB (~3.8MB)`, set by Supabase in
`/etc/postgresql-custom/conf.d/generated-optimizations.conf` for this
instance class, alongside `shared_buffers=224MB`, `max_connections=60`,
`max_worker_processes=6`.

Evidence: `pg_stat_wal` showed 1,780,856 `wal_buffers_full` and 1,789,588
`wal_write` for only 116,346 `wal_records` — ~15x write amplification.
`wal_level=logical` is required (Realtime is genuinely in use by both apps).

Not actionable from our side:
- `ALTER SYSTEM` unavailable (`is_superuser=off`)
- `pending_restart=true` is stale: `setting` == `reset_val`, so a restart
  applies nothing new
- The config file is regenerated by Supabase on compute changes

Only real fix is a larger compute instance. Deliberately left alone.

## Ruled out

- Table bloat — near-zero dead tuples across all app tables
- Autovacuum — keeping up; checkpoints timed (573) not requested (3)
- Realtime subscription leak — 4 `notifications` channels are legitimate
  (web `NotificationMenu` + 2 mobile screens), all with `removeChannel`
  cleanup. `lib/realtime-topic.ts` churn is by design.
- Outbox cron — 288 runs/24h @ 118ms, already optimized by
  `20260818180000_reduce_outbox_cron_io.sql`
- Cron `job startup timeout` failures — all from the 2026-08-18 restart
  window, not recurring
